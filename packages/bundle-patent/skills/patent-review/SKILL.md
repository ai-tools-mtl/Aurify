# 审查路由：走 patent_review 工具

专利项目的审查由确定性链路执行：固定 workflow 脚本按版本化 rubric 逐维并发多轮独立子代理评分，加权汇总后把报告写入 `review/<目标>.review.md`。脚本与 rubric 都是宿主数据，模型既不能代替它评分，也不应手写审查报告——自己即兴审出来的"报告"没有维度权重、没有多轮独立性，也不是可追溯的评分产物。

## 程序

1. 用户要求审查时（无论用什么措辞），先确认审查目标：单个章节文件、`application/` 三件套，还是整个项目目录（目录目标会把全部 Markdown 按名序拼接后逐维评分）。
2. **直接调用 `patent_review` 工具**（参数 `target` 传目标相对路径）。该工具与用户从输入框派发的 `/patent-review` 命令走同一条宿主侧链路，评分完全一致；口语请求不要让用户自己去派发命令。
3. 用户明确想自己操作时，可以告诉他输入 `/patent-review` 从命令触发列表选中成 chip 后补目标路径——两条路等价。目标路径相对当前工作目录：审查整个项目传 `.`（当前目录就是项目时）或项目目录名，单章传如 `chapters/03-background.md`。
4. 报告生成后按维度均分、各次评分与失败次数逐项解读，把扣分点落成具体修改建议；解读与建议一律用简体中文写。

## 红线

- 不自己给交底书或申请文件打分，不在 `review/` 里手写任何"审查报告/审查意见"文件——即使那样看起来更快；评分结构与报告格式必须来自 patent_review 工具或 /patent-review 命令。
- `review/` 目录由审查链路独占。
- 工具报错时把错误原文转告用户（常见：目标路径不存在、会话缺工作目录），不要绕过工具改用手写审查。
