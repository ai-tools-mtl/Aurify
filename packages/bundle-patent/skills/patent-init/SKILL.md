# 交底书项目 Init：点子评估 + 五方对齐访谈

## 目标

把用户带来的技术点子，先过一个价值判断（值不值得写），再收集成一份满足「五方对齐」的技术交底摘要（brief.md）。五方对齐借自专利撰写实践：**现有技术缺点 → 技术问题 → 有益效果** 三方数量大致一致、语义对应，方案逐项回应问题，效果逐项对应方案——对齐了，交底书的骨架就立住了。

## 点子评估（访谈前，先判断再动笔）

用户抛来的小点子先过价值判断——用户的表述是待检验的起点，不是最终答案。开始前先做**环境自检**：调用 `patent_setup_check` 工具（宿主侧工具，MCP 服务未启用时也能调用——它正是用来发现这一情况的）一次性检查 MCP 服务行、检索通道、docker 渲染/实验、镜像与命令策略——受限项如实告知用户并给配置方法（能由你执行的配置直接做，如 docker pull 预热；需要用户操作的给出一句话步骤），配置后复检。**MCP 未启用时你可以直接代写配置**：用写文件工具在 `~/.dsh/patent-services.yaml` 写两行——`mcp_enabled: true` 加 `mcp_project_dir: <patent-services 源码目录的绝对路径>`（路径原样直写，不要经 shell echo/转义——`G:\02-…` 里的 `\02` 会被某层折叠成控制字符，python 侧会拒读整个文件；自检的「配置文件损坏」行会点名这种坏行）。写完请用户完整重启桌面壳（MCP 行在进程启动时装载，仅新开会话无效），重启后调 `patent_setup_check` 复检——报告区分「已装载」与「待重启」，显示「已装载」前不要把 MCP 工具当可用；其余通道（docker、镜像、检索）改完即生效无需重启。**检索通道不可达时的评估边界**：可以先拆特征、可以先进入访谈收集维度，但三档结论必须等检索可用后才能给——没有检索证据的评估结论不成立（见 patent-research 的纪律），向用户说明这一顺序。全程与用户的对话使用简体中文：

1. **拆特征**：从点子里提取 2~3 个核心技术特征（做什么、靠什么关键手段做到）。
2. **检索现有专利**：按 patent-research skill 用特征词多轮检索（`search_cn_patents`），初筛命中的最接近几篇逐篇用 web_fetch 读明细（摘要 + 权利要求 1）。
3. **形成三档结论**，当面向用户说明并附公开号证据：
   - **建议写**——存在明确的差异化空间：最接近的对比文件缺什么、本点子补什么，说得清楚；
   - **收窄后写**——大方向现有技术密集，但存在具体缝隙：指出是哪几篇、缺哪个特征组合，按收窄后的方向继续；
   - **不建议写**——核心技术已被公开（给公开号）、无实质技术贡献（纯商业规则、界面布局等非客体内容）、或宣称效果与技术手段挂不上钩。给出理由与（若有）邻近的可写方向。
4. **与用户对话确定方向**：把判断和证据摆到桌面上，用户可以反驳，也欢迎用户反驳——谁对听谁的；发现用户方案的矛盾、过度声称、与检索结果冲突时直接指出。结论由用户拍板；用户坚持原方向时照做，但在 brief.md 评估节保留风险标注。
5. 评估结论（三档之一 + 关键证据 + 选定方向）写进 brief.md 的评估节，作为后续五方的地基。

## 维度与就绪判据

| 维度 key | 章节 | 核心/边缘 | 说明 |
|----------|------|-----------|------|
| field | 所属技术领域 | 核心 | 发明属于哪个技术领域、哪些专业分类 |
| background | 背景技术 | 核心 | 现有技术有哪些、缺点是什么（按点列举） |
| problem | 技术问题 | 核心 | 要解决的技术问题，逐条对准缺点 |
| solution | 发明内容 | 核心 | 整体方案：结构/流程/关键组件及各自解决的子问题 |
| effect | 有益效果 | 核心 | 相比现有技术的优势，尽量可量化 |
| name | 名称 | 边缘 | 可由领域+方案提炼，不卡就绪 |
| key_points | 关键点与保护范围 | 边缘 | 生成期补全 |
| drawings | 附图 | 边缘 | 生成期补全 |

**就绪 = 五个核心维度全部收集 + 缺点/问题/效果三方条数偏差 ≤ 1。** 判据的唯一权威是 `patent_brief_coverage` 工具，不要凭感觉宣布就绪。

## 访谈程序

1. 一次聚焦一两个维度，用具体、封闭的问题引导（"现在的方案是怎么做这件事的？""这一步卡在哪里？"），不要一次抛出十个问题。
2. 用户每轮补充信息后，把已收集的内容按维度整理，调用 `patent_brief_coverage`（把每个维度已收集的草稿内容作为参数传入，未收集的维度省略）。
3. 根据返回的 missing 列表继续追问；aligned=false 时优先补齐偏少的一方（通常是有益效果——追问"每个效果对应方案的哪个组件？有量化数据吗？"）。
4. 现有技术缺点维度继续按 patent-research skill 滚动查新：评估阶段的粗检索不够时细检索收紧，用真实命中校准追问——缺点是文献里真实存在的，还是只凭用户体感；筛出的对比文件逐步积累进 `reference/prior-art.md`。检索通道不可达时向用户说明，可先继续访谈、代理可用后再补查，不编造对比文件。
5. 缺点/问题要用**技术语言**收集：商业痛点（"成本高""不好卖"）要追问到技术机制（"具体是哪个环节的开销、什么导致的"）。
6. `ready=true` 后向用户复述五方内容确认，然后进入建档（下节）。

## 建档约定

在项目目录（用户指定，或当前目录下的拼音/英文短名子目录）建立：

```text
<project>/
  patent.yml               # formatVersion: 1; name; status: init|drafting|review|application|done（审查阈值 reviewThreshold、审查轮次 reviewPasses 为后续可选键）
  brief.md                 # 开头是评估节（三档结论+证据+选定方向+风险标注），后接五方对齐摘要（按维度分节）
  chapters/                # 八个基础章节文件，空章建占位；涉及实验/量化效果的项目另有 09-verification.md 实验验证章（实验成形时建，不必空占位）
    01-name.md 02-field.md 03-background.md 04-problem.md
    05-solution.md 06-effect.md 07-key-points.md 08-drawings.md
  figures/                 # 附图目录：最外层只放最终插入文档的 .png；可编辑源在 figures/source/（.drawio、.html 等），中间产物在 figures/tmp/
  review/                  # 审查报告
  exports/                 # 导出的 docx/pdf
  reference/               # 参考材料：对比文件清单 prior-art.md、检索历史账本 search-history.md（search_cn_patents 带 project_dir 时自动追加）、解析的参考文献
```

建档完成后向用户说明目录结构，然后按 patent-chapters skill 开始起草。
