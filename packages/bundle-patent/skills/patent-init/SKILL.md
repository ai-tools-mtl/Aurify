# 交底书项目 Init：点子评估 + 五方对齐访谈

## 目标

把用户带来的技术点子，先过一个价值判断（值不值得写），再收集成一份满足「五方对齐」的技术交底摘要（brief.md）。五方对齐借自专利撰写实践：**现有技术缺点 → 技术问题 → 有益效果** 三方数量大致一致、语义对应，方案逐项回应问题，效果逐项对应方案——对齐了，交底书的骨架就立住了。

## 环境自检门（第 0 步，先于评估与访谈，导入路径同样适用）

评估动笔前先做**环境自检**：调用 `patent_setup_check` 工具（宿主侧工具，MCP 服务未启用时也能调用——它正是用来发现这一情况的）一次性检查 MCP 服务行、检索通道、docker 渲染/实验、镜像与命令策略。能由你执行的配置直接做（如 docker pull 预热、代写配置文件）；需要用户操作的给出一句话步骤。

**🔴 STOP——报告呈现后必须停在本门，等用户回复**：把自检结果如实呈现给用户——哪些项就绪、哪些受限、你已代做了什么、还差哪几步（逐项一句话）——然后结束本轮等待用户处理。**唯一的例外是检索通道**：它不可达（常见原因是 VPN/代理没连）时，向用户提问「**是否跳过查新、先继续写作？**」——用户明确选择跳过，才允许带着检索受限往下走；其余受限项（MCP 服务行、docker、镜像、drawio、命令策略）**一律不给跳过选项**，只给一句话修复步骤，等用户修复后复检通过。**门未通过之前不得进行任何后续操作**：不拆特征、不检索、不访谈、不回答点子本身的问题——用户最初的提问只登记、不展开。

**通行条件只有三条**：① 受限项为空——报告全部就绪，随即进入下方可专利性评估程序；② 全部受限项已修复且复检通过；③ 其余受限项已全部修复复检、仅剩检索通道，且用户对上面的问题明确答复跳过——在用户当前目录的reference/prior-art.md 写「查新不可用：待补查」标记（项目尚未建档时的暂存落点；建档后移交 `<project>/reference/prior-art.md`）。先继续访谈与写作，但需要检索支撑的三性建议仍要等检索恢复后补证据，见 patent-research。没有第四条「我判断影响不大就替用户跳过」——除检索通道外任何项都不跳过，跳不跳检索也由用户拍板。

**MCP 未启用时你可以直接代写配置**：先读取并保留 `$DSH_HOME/patent-services.yaml`（默认 `~/.dsh/patent-services.yaml`）中的已有偏好，再用文件工具合并启用配置——`mcp_enabled: true` 加 `mcp_project_dir: <patent-services 源码目录的绝对路径>`（路径原样直写，不要经 shell echo/转义——`G:\02-…` 里的 `\02` 会被某层折叠成控制字符，python 侧会拒读整个文件；自检的「配置文件损坏」行会点名这种坏行）。无源码检出时可改用 `mcp_enabled: true` 加 `mcp_wheel: true`（uvx 从 PyPI 解析，未锁定本版，无需预先安装 wheel）。写完请用户完整重启桌面壳（MCP 行在进程启动时装载，仅新开会话无效），重启后调 `patent_setup_check` 复检——报告区分「已装载」与「待重启」，显示「已装载」前不要把 MCP 工具当可用；其余通道（docker、镜像、检索）改完即生效无需重启。

**检索通道不可达时的评估边界**（用户选择带受限继续时适用）：可以先澄清披露时间线、拆特征、进入访谈收集维度，但需要检索支撑的三性建议必须等检索可用后才能给——没有检索证据的评估结论不成立（见 patent-research 的纪律）。例外：客体排除或已核实独立否定理由的提前否定可以先行，未执行的检索环节如实注明。每轮访谈都提醒检索通道仍未恢复。

## 已有文档导入（用户带来现成交底书/说明书时）

适用：用户带着**已写好的**交底书或说明书 Word 文档来——从它继续修订、审查、补附图或推进申请文件，而不是从点子重新访谈。程序：

1. **环境自检门照走**（第 0 步不豁免）——导入工具在 MCP 服务里，自检未过同样不得动手。
2. **调 `import_patent_document(project_dir, document_path)`** 导入：章节按标题映射进 `chapters/01–08`，未映射的一级节顺延为附加章，brief.md 五维骨架与 patent.yml（缺时）一并生成。用户还没建项目时直接给目录——工具会把目录建构成完整项目；拿不准解析效果可先 `parse_disclosure_docx` 看纯文本。
3. **向用户复述导入报告**：映射了哪些章、哪些节未导入（权利要求书/摘要属申请文件材料，预期跳过、后续按 patent-application 从章节重写）、哪些章是空占位、表格/图片未导入的计数。**原文档不是交付物**——交付物一律从 chapters 重新导出。
4. **跑 `patent_loop` 让流程接管**：章节门会点名空占位章，逐章补齐；正文引用的公开号按 patent-research 记入项目查新账本reference/prior-art.md（流程 chapters 门会拦截缺账本的公开号）。
5. **查新与评估补强**：导入项目省掉访谈，不省掉把关——检索证据（patent-research）照做，评估结论可后置到修订轮，但审查前 brief.md 评估节要有依据；已有文档不等于已查新。

## 可专利性初步评估（访谈前，先判断再动笔）

用户抛来的点子先过价值判断——用户的表述是待检验的起点，不是最终答案。自检门通过后从这里开始。全程与用户的对话使用简体中文。「可专利性四步自检」指客体、新颖性、创造性、实用性四类判断；下方 1–7 是它们的执行程序（先澄清再检索、逐项对比、三步法论证、实用性与公开核查、形成建议）。点子也可以来自 repo-mining 挖掘的候选文件（`repo-mining/<owner>__<repo>/candidates/` 下，自带披露记录、证据链与发明人候选）——证据链先用 `repo_verify_evidence` 对账，评估按本节同一程序执行，不另设简化判据。已有文档导入的项目同样适用本程序；评估后置到修订轮时，评估状态先按「未评估」留档。评估是对「当前方案＋拟申请类型」的初步建议，不是授权结论；关键事实不足时给「暂缓评估」，不强行归入三档。

1. **事实澄清与客体初筛**：先收集披露时间线——仓库/论文/演示/发布包等何时可被公众看到、已公开了哪些内容、是否已有申请及优先权主张；自己的公开同样可能构成现有技术，commit 时间不等于首次公开时间。客体疑点（纯算法、商业规则、信息呈现、美学设计等）先补问再判断：整体分析技术手段、技术问题与技术效果，既不因「含算法」直接排除，也不因「在计算机上运行」直接认可。确认落入排除事项（专利法第 5 条、第 25 条，含未与技术手段结合的纯算法/商业规则）且有依据时提前结束，给限定范围的「不建议写（客体）」并提示替代路径（商业秘密等须各自符合条件），未执行的检索环节如实注明。
2. **明确评估对象**：形成拟保护方案的完整特征组合与关键相互关系（2~3 个检索词不等于全部限定特征），标注方案版本与拟申请类型；类型未定时按发明/实用新型两条路线分别记录——方法类方案仅可走发明。尚不能形成方案的暂缓评估，记录缺什么。
3. **检索与证据核查**：按 patent-research 的检索程序执行并达到其「检索收口」要求，登记检索日期、覆盖范围与材料缺口。
4. **逐项单独对比**：把拟保护特征组合逐项对照**每一篇**相关公开技术方案（不是只比「最接近的一篇」），记录特征对应位置（明细页的具体权利要求/段落/附图）、时间资格（现有技术／潜在抵触申请／待确认）与未能确认的内容。单篇公开全部特征才谈新颖性受挫；多篇组合的覆盖转创造性论证，不作新颖性否定。先确定本案相应主题的判断日期（申请日；主张有效优先权的，核查该主题适用的优先权日），再比较在先申请的申请及公布日期：判断日期前已公开的技术内容可作为现有技术；在先申请早于判断日期、其文件在判断日期当日或以后公布的，核查其是否满足中国抵触申请条件，先列「潜在抵触申请」。检索时已经公布不等于现有技术；尚未公布是在公开检索中无法排除的盲区，不等于已确认抵触申请。申请人本人的在先申请同样按这些时间关系核查，日期或适用条件不明则待确认。
5. **创造性论证**：按三步法组织——最接近的现有技术；区别特征在方案中的作用与效果→实际解决的技术问题；现有技术整体与有依据的公知常识是否给出改进动机与技术启示。不把区别特征倒装成问题答案（事后分析）；「公知常识」也要给依据；抵触申请不作为创造性组合的依据。按拟申请类型分别分析：发明要求突出的实质性特点和显著的进步，实用新型要求实质性特点和进步；实用新型的技术启示分析一般着重所属技术领域，跨相近或相关领域须说明明确启示，一般引用一项或两项现有技术，简单叠加等情形可依具体情况引用多项，不能把数量当作绝对上限，也不能机械套用发明的尺度。类型未定时分别记录各路线依据与建议，切换类型后核查原分析是否适用。长期难题、技术偏见、预料不到的效果、商业成功仅作有证据的辅助因素。
6. **实用性与充分公开核查**：分别记录——能否制造或使用、有无积极效果（第 22 条第 4 款）；说明书是否清楚完整到本领域技术人员能实现（第 26 条）。不能实现与尚未说明清楚分开处理；实验或仿真只支持其条件下的实现与效果。对照 2026 施行的新审查示例：手段未在申请文件记载但属公知常识，不构成公开不充分（指南例 20）；既未记载也非公知才是硬伤（例 21）。AI/模型类候选按新撰写要求预核——必要模块、层级、步骤、参数，以及模型与场景的结合方式、输入输出关系是否拿得到；拿不到的列待补项。
7. **形成建议并留档**：按下方判据给出三档建议或暂缓，按下方状态恢复程序落盘——落盘字段以「评估状态与恢复」末段的持久化清单为准；用户坚持原方向时照做，依据与风险照记，不改写事实结论。留档随附**技术缺口摘要**（研发参考，非法律结论）：基于已核查材料归纳已有方案已解决什么、公认仍未解决什么、本方案区别特征对应哪个缺口、还有哪些缺口值得继续研发投入；逐条标注来源文献与剩余不确定性，不替研发拍板方向——挖掘与评估能帮研发看清下一步值得研究的技术问题，但不能替代研发。

**三档判据**：

- **建议写**——检索已收口、无决定性缺口；已核查材料范围内未发现足以否定新颖性的公开；存在有证据支持的创造性论证空间；实现路径与充分公开所需内容已基本说明，剩余事项及其影响明确。禁止捷径：「一篇没覆盖所以新颖性成立」「没搜到组合所以创造性成立」都不成立。
- **收窄后写**——指出可追溯的具体改进或限定及其效果，并对收窄后的组合按同等证据要求重做适用核查；无法核查就只列待评估方向，不给正面建议。
- **不建议写**——有事实和分析支持的具体理由：客体排除、完整方案被公开、缺乏创造性论证空间、无法实现等；列出适用依据与范围。仅因仓库公开、缺实验、暂未检索或用户暂未解释清楚就否定，不允许。
- **暂缓评估**（不是第四档建议）——披露时间、关键特征、对比文件全文、优先权或技术启示等决定性材料缺失：列出待补项、影响哪项判断、恢复条件。把未知写成满足或不满足，不允许。

**判定顺序**：有已核实、足以独立支持否定的理由时，先给限定范围的「不建议写」，其余未知项如实保留并注明未执行环节；但若未知项可能推翻否定依据本身（如该公开是否早于有效日期尚不明），则不能提前否定。无独立否定依据而存在决定性缺口时暂缓；无该缺口才判断建议写/收窄后写。原方案的否定不自动覆盖新方向、其他申请类型或尚未核查的收窄方案。「已核实」以 patent-research 的位置核查为准（读过相关权利要求与说明书段落并记录位置）——**只有通用网页线索级命中、未读明细页核实的文献，不构成「已核实的独立否定依据」**：不得据此给出「不建议写/建议写」的实质方向，此时给暂缓，暂缓说明里可附风险预判与收窄待评估方向（标明为预判，非结论）。

**统一边界尾注**（每次评估结论随附；客体提前终止时改用「尚未进行检索」措辞）：

> 以上是针对当前方案、基于所列材料的初步建议。检索日期、覆盖范围和遗漏见评估记录；未发现不等于不存在。已公开的潜在抵触申请可检索核查，检索时尚未公开的在先申请（包括申请人自己的申请）无法通过公开检索排除。专业检索与评估仍有边界，本建议不保证授权。

## 评估状态与恢复（所有材料阶段适用）

评估状态（未评估/评估中/暂缓评估/已形成建议/待重评）由本技能维护在 brief.md 评估节；材料就绪以 `patent_brief_coverage` 为准，成稿以 `patent_loop` 为准。恢复评估是材料阶段推进前的独立动作，**不受 init/align 限制**；chapters、review、export 或 complete=true 时收到补证、发现变化，也按本节组织，检索委托 patent-research，不伪造工具阶段或 gaps。

1. **读取与核对**：首次评估记「未评估」，开始核查后转「评估中」；缺历史评估的旧项目按未评估处理。恢复或接手时先读当前记录、待补项及 reference/，核对方案、申请类型、判断日期与证据版本，不能直接沿用旧建议。
2. **决定状态**：决定性材料缺失且无独立否定依据时转「暂缓评估」，保存「缺什么—影响对象及判断—补到什么程度可恢复—下一步」。有已核实独立否定依据，或完成适用核查并达到三档判据时，转「已形成建议」，记录建议、依据和适用范围。缺口事实可以来自用户未提供信息或工具失败，不要求先取得检索命中。
3. **标记变化**：新证据、披露或优先权日期更正、贡献特征或申请类型变化、效果或实现依据改变时，先记录影响分析；实质影响已有建议的，更新方案/证据记录版本和评估版本，转「待重评」，明确旧建议不再适用于哪些对象。纯排版或不影响建议的新增材料，记录理由并保留适用建议，不无差别重跑。
4. **实际恢复**：补证达到恢复条件后，暂缓/待重评转「评估中」；复核受影响的时间资格、特征对比、技术启示、实现和效果及其依赖环节，必要时重开检索。完成后重新作出建议及替代关系；仍有决定性缺口则继续暂缓，不能仅删除待办或更改状态。旧评估和依据保留为历史。
5. **范围与交付**：暂缓期间可继续不依赖缺失事实的澄清、访谈与资料整理；已有用户授权覆盖带缺口继续准备材料时可沿用，否则先保存缺口和可继续范围，等用户选择后再起草、审查或导出。既有环境门和检索不可达的用户选择机制不变。材料 complete=true 不改变评估状态；交付随附当前评估版本、适用对象和未清事项，不给受影响对象正面建议。

评估记录必须持久化保存方案标识与版本、申请类型、判断日期及依据、证据记录版本、评估版本、状态、建议及当前适用性、检索截止日期、变化摘要、待补项、恢复条件和下一入口。项目未建档时，普通点子先存用户选定目录的 brief.md 评估草稿，不为此提前建 patent.yml；来自 patent-mining 的候选在建档前保存在候选文件，建档时将当前记录移交 brief.md 并同步版本引用，后续以 brief.md 为准。方案或证据未变的状态流转也应记录时间和原因；版本更新保留历史及替代关系。

## 维度与就绪判据

| 维度 key | 章节 | 核心/边缘 | 说明 |
|----------|------|-----------|------|
| field | 所属技术领域 | 核心 | 发明属于哪个技术领域、哪些专业分类 |
| background | 背景技术 | 核心 | 现有技术有哪些、缺点是什么（按点列举） |
| problem | 技术问题 | 核心 | 要解决的技术问题，逐条对准缺点 |
| solution | 发明内容 | 核心 | 整体方案：结构/流程/关键组件及各自解决的子问题 |
| effect | 有益效果 | 核心 | 相比现有技术的优势，尽量可量化 |
| name | 名称 | 边缘 | 可由领域+方案提炼，不卡就绪 |
| key_points | 关键点与保护范围 | 边缘 | 生成期补全 |
| drawings | 附图 | 边缘 | 生成期补全 |

**就绪 = 五个核心维度全部收集 + 缺点/问题/效果三方条数偏差 ≤ 1。** 判据的唯一权威是 `patent_brief_coverage` 工具，不要凭感觉宣布就绪。

## 访谈程序

1. 一次聚焦一两个维度，用具体、封闭的问题引导（"现在的方案是怎么做这件事的？""这一步卡在哪里？"），不要一次抛出十个问题。
2. 用户每轮补充信息后，把已收集的内容按维度整理，调用 `patent_brief_coverage`（把每个维度已收集的草稿内容作为参数传入，未收集的维度省略）。
3. 根据返回的 missing 列表继续追问；aligned=false 时优先补齐偏少的一方（通常是有益效果——追问"每个效果对应方案的哪个组件？有量化数据吗？"）。
4. 现有技术缺点维度继续按 patent-research skill 滚动查新：评估阶段的粗检索不够时细检索收紧，用真实命中校准追问——缺点是文献里真实存在的，还是只凭用户体感；筛出的对比文件逐步积累进项目查新账本reference/prior-art.md。检索通道不可达时按「检索通道不可达时的评估边界」执行，不编造对比文件。
5. 缺点/问题要用**技术语言**收集：商业痛点（"成本高""不好卖"）要追问到技术机制（"具体是哪个环节的开销、什么导致的"）。收集时带**双问校准**：「已有技术已经解决了什么？本方案解决的是它们**没有解决/解决不了**的哪个问题？」——答案指向「同一个问题做得更好/更快」时如实记录，并在评估节标记为创造性风险线索：性能优势不能直接当创造性论证，重点转向区别特征自身的作用与效果（环节 5 复核）；这一问也为背景技术章「已有方案解决了什么、没解决什么」的写法提供素材。
6. **辅助因素按需采集**：问到效果时顺带收集长期未解难题、行业技术偏见、预料不到的效果、商业成功的材料——注明来源、对照条件与因果关系；没有材料就记「未提供/待核」，不强行填出正面事实，也不让这些因素替代三步法论证。
7. `ready=true` 后 🔴 向用户复述五方内容确认，用户确认后才进入建档（下节）。

## 建档约定

在项目目录（用户指定，或当前目录下的拼音/英文短名子目录）建立：

```text
<project>/
  patent.yml               # formatVersion: 1; name; status: init|drafting|review|application|done（审查阈值 reviewThreshold、审查轮次 reviewPasses 为后续可选键）
  brief.md                 # 开头是评估节（方案/证据/评估版本、申请类型、判断日期、状态、建议及适用性、收口理由、尾注、待补项和恢复条件），后接五方对齐摘要（按维度分节）
  chapters/                # 八个基础章节文件，空章建占位；涉及实验/量化效果的项目另有 09-verification.md 实验验证章（实验成形时建，不必空占位）
    01-name.md 02-field.md 03-background.md 04-problem.md
    05-solution.md 06-effect.md 07-key-points.md 08-drawings.md
  figures/                 # 附图目录：最外层只放最终插入文档的 .png；可编辑源在 figures/source/（.drawio、.html 等），中间产物在 figures/tmp/
  review/                  # 审查报告
  exports/                 # 导出的 docx/pdf
  reference/               # 参考材料：对比文件清单 prior-art.md、检索历史账本 search-history.md（search_cn_patents 带 project_dir 时自动追加）、解析的参考文献
```

其中 `01-name.md` 只写最终发明名称**一行**——候选发散、名称间比较、结构拆解留在会话或 `review/`，写进文件会原样进交付物的"一、名称"节（导出器与流程章节门都会点名拦截）。

建档完成后向用户说明目录结构，然后按 patent-chapters skill 开始起草。
